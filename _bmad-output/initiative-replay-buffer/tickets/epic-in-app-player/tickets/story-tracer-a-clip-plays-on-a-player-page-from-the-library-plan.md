# Story 14.2: a Clip plays on a player page from the Library

App and Platform.Desktop only, on AD-27. Plan for the coordinator's checkpoint; no product code yet.

## Proof behind this plan (throwaway, scratchpad)

A scratch copy of the whole path ran on this PC on 2026-11-05: a CsWin32 interop library built with Platform.Desktop's settings (`allowMarshaling: false`, `DisableRuntimeMarshalling`, `IsAotCompatible`, warnings as errors), and a WPF window. It built with 0 warnings and played `h264-clip.mp4`, the research's four-Track 1280×720 fixture.

- **Open:** the file was opened with `FileShare.ReadWrite | FileShare.Delete` and handed to `MediaSource.CreateFromStream(stream.AsRandomAccessStream(), "video/mp4")`. It opened in about 0.7 s. Track names came back as Game, Mic, Discord and Desktop.
- **Tracks:** Windows picked index 2 at open; setting index 0 took.
- **Picture:** the frame server copied into a shared D3D11 texture, a D3D9Ex texture opened on the same handle, and a `D3DImage` showed its surface. WPF's own render of the `Image` was 96 % picture, with the right colours, and a frame was copied every 1/60 s while playing.
- **First frame:** with the player paused, setting `Position` to 0 delivered one frame, so the page can open paused on its first frame.
- **Sharing:** while it played, another handle renamed the file and then deleted it, both successfully, and playback carried on.
- **Teardown:** a present queued to the UI thread after teardown threw (`AddDirtyRect` with no back buffer). Hence the close order below.
- **Seeking while paused:** a seek to 3 s delivered *no* frame, and playback later resumed from about 0. That's for 14.5 to settle, and is noted under Follow-ups.

## Changes

### Platform.Desktop (CsWin32; AD-2, AD-14, AD-27)

- **`NativeMethods.txt` gains:** `D3D11CreateDevice`, `D3D11_SDK_VERSION`, `ID3D11Device`, `ID3D11DeviceContext`, `ID3D11Texture2D`, `D3D11_TEXTURE2D_DESC`, `IDXGIResource`, `IDXGISurface`, `Direct3DCreate9Ex`, `D3D_SDK_VERSION`, `IDirect3D9Ex`, `IDirect3DDevice9Ex`, `IDirect3DTexture9`, `IDirect3DSurface9`, `D3DPRESENT_PARAMETERS`, `D3DUSAGE_RENDERTARGET`, `D3DCREATE_HARDWARE_VERTEXPROCESSING`, `D3DCREATE_MULTITHREADED`, `D3DCREATE_FPU_PRESERVE`, `CreateDirect3D11SurfaceFromDXGISurface`, `IInspectable`. All are generated by 0.3.367 (proven).
- **`VideoSurface`** (public, sealed, `IDisposable`, unsafe, in the style of `ShellThumbnail`):
  - `new VideoSurface(width, height, hwnd)` creates:
    - a D3D11 device (hardware, BGRA support);
    - a `B8G8R8A8_UNORM` texture with render-target and shader-resource binding and `MISC_SHARED`;
    - its shared handle (`IDXGIResource.GetSharedHandle`);
    - a D3D9Ex device (HAL, windowed, 1×1, multithreaded, FPU preserve) on the App's window;
    - an `A8R8G8B8` render-target texture opened on that handle, and its level-0 surface;
    - the WinRT surface (`CreateDirect3D11SurfaceFromDXGISurface`).
  - `BackBuffer` (the `IDirect3DSurface9*` for `D3DImage`), `Direct3DSurface` (the WinRT `IDirect3DSurface`, through `MarshalInterface<>.FromAbi`; it passes the AOT analyzers), `Width`, `Height`, `Flush()` (the D3D11 context's flush after a copy), and `Dispose()`, which releases all of it in reverse order.
  - A failed step releases what was made and throws.

### App: the player seam (`Library/Player/`)

- **`IPlayer`** (internal, `IDisposable`):
  - `Task<PlayerMedia> OpenAsync(Stream file)`, which throws `PlayerException` (with the reason) on `MediaFailed` or a 10 s timeout;
  - `ShowFirstFrame()`, `Play()`, `Pause()`, `bool IsPlaying`;
  - `int SelectedTrack { get; set; }`, `TimeSpan Position { get; }`;
  - `event Action FrameAvailable` (on any thread), `void CopyFrame(VideoSurface target)`, `event Action Ended`.
  - `PlayerMedia(int Width, int Height, TimeSpan? Duration, IReadOnlyList<string> TrackNames, bool VideoDecodable)`.
  - The seam is just wide enough for 14.4 to 14.6 (Tracks, position, decoder status) without changing its shape for the tracer's tests.
- **`WindowsMediaPlayer : IPlayer`:** the WinRT `MediaPlayer` with `AutoPlay` false, `IsVideoFrameServerEnabled` set before the source, and `MediaPlaybackItem` from the stream.
  - `ShowFirstFrame` sets `Position` to 0 while paused, as proven.
  - `VideoDecodable` is the video Track's `SupportInfo.DecoderStatus == FullySupported`; 14.6 uses it.
  - `Dispose` turns the frame server off, unhooks every event, sets `Source` to null and disposes the player.

### App: the player page

- **`PlayerPage`** (view model, `IDisposable`):
  - It takes the absolute path, the row's name, an `IPlayer` and an `openRead` function. The default opens `FileMode.Open, FileAccess.Read, FileShare.ReadWrite | FileShare.Delete`.
  - **`OpenAsync`:** it opens the stream, then the player, sets `SelectedTrack = 0` (AD-27), and calls `ShowFirstFrame`. The state is then `Paused`.
  - States: `Opening`, `Paused`, `Playing`, `Ended` (back to paused on the last frame) and `Failed`. `Failed` shows one plain line, "This file couldn't be played.", plus "Open in default player"; 14.6 replaces it with the codec messages.
  - `PlayPauseCommand` plays and pauses; from `Ended`, it plays from the start.
  - **`Dispose`:** marks the page closed, disposes the player (frames stop first), then the stream. Safe to call twice.
- **`PlayerView`** (UserControl):
  - The video is an `Image` on a `D3DImage`, in a black backdrop that fills the page under the breadcrumb, with `Stretch` `Uniform` for the letterbox. A minimal bottom bar sits over the video: the play/pause button and the state line, in the looks' button and caption styles. 14.5 adds the transport and 14.4 the Track list.
  - **Frames, all on the UI thread:**
    - `FrameAvailable` sets a pending flag and posts one present, so it's coalesced (the event can fire at the display's refresh rate).
    - The present returns if the page is closed or the front buffer is unavailable.
    - It (re)creates the `VideoSurface` when the wanted size changed: the video's aspect fitted into the `Image`'s pixel size (DPI applied), even sides, never larger than the video.
    - Then it calls `CopyFrame`, `Flush`, and `Lock`, `AddDirtyRect`, `Unlock`.
  - **Resizing:** the old surface stays up, scaled by WPF, until the next frame, so a resize while paused never blanks the picture.
  - **Lost front buffer:** `IsFrontBufferAvailableChanged` (a lock screen or display change) recreates the surface when it comes back, and asks for a frame (`ShowFirstFrame` if paused at 0, otherwise the next frame while playing).
  - **Unload and close:** the back buffer is set to `IntPtr.Zero` after the page is marked closed, and then the surface is disposed. That's the order the proof's crash calls for.

### App: the Library and the shell

- **`LibraryPage`:**
  - gains `DrillIn = new DrillIn("Library")`, `PlayerPage? Player`, and constructor parameters `Func<IPlayer>? player` (default `() => new WindowsMediaPlayer()`) and `Func<string, Stream>? openRead`.
  - **`OpenFocused`** (Enter and double-click) opens the player for a finished row: it checks the file exists (as `Existing` does), creates the `PlayerPage`, calls `DrillIn.Open(row.Path, row.Name)`, then `OpenAsync`. On a row being written it does nothing (AD-27).
  - **`OpenCommand`** keeps today's shell open. Its label becomes "Open in default player" in the command bar and the context menu.
  - **`DrillIn.Closed`** disposes the player page.
  - **`Render`:** when the open page's item is no longer in the Library (deleted, renamed or cleaned up), it closes the drill-in, which releases the file.
- **`LibraryView`:**
  - shows the list or the `PlayerView`, by `DrillIn.IsOpen`; the list is hidden, not unloaded, so its scroll and focus survive.
  - **Key guard:** while the player is open, `OnViewPreviewKeyDown` and the list's mouse handlers don't act on the list. Delete, Space, F2 and Ctrl+A would otherwise reach the hidden selection, and Delete would delete the file being played.
  - On `Closed`, focus goes back to the row, as Games does.
- **`MainViewModel`:**
  - `CurrentDrillIn` is the Library's drill-in when the Library is shown, so the breadcrumb, Esc, Alt+Left, the mouse's Back button and reselecting the Library nav item all work as 10.10's do. `IsDrilledIn` follows the Library's drill-in too.
  - `NavigationChanged` closes the Library's drill-in when a settings page is selected, which releases the file.
  - Hiding the window (`IsWindowShown` false) pauses the player.
- **`MainWindow`:** no change; it already routes through `CurrentDrillIn`.
- **Ticket text:** 14.2's description reads "The MediaPlayer is with IsVideoFrameServerEnabled on…". That's fixed to "The MediaPlayer has IsVideoFrameServerEnabled on…" in `tickets.toml`.

## QA round 1 fixes (2026-11-05)

QA failed round 1 at `b11f216` with one blocking finding and four others.

1. **[blocking] References after `Dispose`:**
   - **Measured:** a scratch probe counted the references left on each COM object after `Dispose`.
     - Disposing the WinRT wrapper (`IClosable.Close`) frees the texture and both devices. But the WinRT surface object keeps 3 references: the wrapper's native reference and CsWinRT's per-interface cache entries, which `Close` doesn't touch. They go only at a GC.
     - Media Foundation keeps none once the player is disposed, whichever is released first.
   - **Fix:** `VideoSurface` disposes the wrapper and then, through public CsWinRT API, its interface references (`GetObjectReferenceForType` for `IDirect3DSurface` and `IDisposable`) and its `NativeObject`. That happens on every resize and in `Dispose`.
   - **New default test:** `VideoSurfaceTests.DisposeReleasesEveryReferenceAtOnceEvenAfterAResize`. With no GC, the old views reach 0 after a resize, and the WinRT surface, the D3D9 texture (which shares its count with its surface level), the D3D11 texture, the D3D9Ex device, D3D9, the D3D11 context and the D3D11 device all reach 0 after `Dispose`.
2. **HRESULTs:**
   - CsWin32's struct methods (`CreateTexture2D`, `GetSharedHandle`, `CreateDeviceEx`, `CreateTexture`, `GetSurfaceLevel`) are `void` and call `ThrowOnFailure` themselves, as checked in the generated source. So every step already throws on failure; the class comment now says so.
   - `PlayerView.Present` catches only `ExternalException` from building the surface. It then releases the surface and calls the new `PlayerPage.ShowFailure()`, which pauses and shows the Failed line.
   - The copy's catch is narrowed to `ExternalException`, `ObjectDisposedException` and `InvalidOperationException`, which skip that frame.
   - New default test: `LibraryPlayerTests.APictureTheGpuRefusesShowsTheFailureAndPauses`.
3. **Front buffer back:** the surface is remade on new devices, and the current frame is redrawn (`OnFrameAvailable`), paused or playing.
4. **Quit:** `ShellApp.QuitAsync` closes the Library's drill-in first, so the player stops and the file and devices are released before the engine shuts down.
5. **Resize:**
   - `VideoSurface` now makes its two devices once, in `new VideoSurface(window)`. `Resize(width, height)` remakes only the texture and its views.
   - `PlayerView` remakes them only after the picture's size has held for 150 ms. Until then it copies into the old texture, drawn scaled.

## QA round 2 fix (2026-11-05)

Round 2 confirmed the references, the front-buffer redraw, Quit and resize. One finding was left: `Present`'s catches were too narrow. `ThrowOnFailure` and CsWinRT map `E_OUTOFMEMORY` to `OutOfMemoryException` and `E_INVALIDARG` to `ArgumentException`, which aren't `ExternalException`, so the App would have crashed from the dispatcher.

- **Fix:** the present's work is now `PlayerView.Draw(page, ensureSurface, show, release)`.
  - Any exception building the surface releases it and calls `page.ShowFailure()`, which pauses and shows the Failed line.
  - Any exception copying a frame skips that frame.
  - Both are commented `catch (Exception)`.
- **Tests, through the real catch:**
  - `LibraryPlayerTests.APictureTheGpuRefusesShowsTheFailureAndPauses` is a theory over `OutOfMemoryException`, `COMException` (DXGI device removed) and `ArgumentException`. Each releases the surface and leaves the page Failed, paused, with Play disabled.
  - `AFrameThatCantBeCopiedIsSkippedAndThePageKeepsPlaying` has the fake's `CopyFrame` throw a `COMException` into a real 64×36 surface: nothing is shown, and the page keeps playing.
