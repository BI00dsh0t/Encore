# Automation State

The single place to resume the unattended build of initiative-replay-buffer after a usage limit or a restart. Every session reads this first and updates it at each checkpoint. It lives on `develop` in the main folder: `%USERPROFILE%\Documents\repos\ReplayBuffer\_bmad-output\initiative-replay-buffer\automation-state.md`.

**To resume:** open the coordinator session (or any new session in this repo), say "continue the automation", and point it at this file. It reads the Queue, checks `git -C <main> log develop` and the board (`python _bmad/method/scripts/tickets.py status _bmad-output/initiative-replay-buffer`), and starts the session for the first row that isn't `done`.

## Standing decisions (builder, 2026-11-01)

- Build everything to the end of the initiative, unattended. The builder is away from the desktop.
- **One fresh session per task** (story, spike, epic slicing, release), started by the coordinator one at a time, so context stays small. Sessions run sequentially: they share `develop` in the main folder.
- Each story runs `bmad-build-auto` on its ticket (unattended plans, implementation and review). No plan-approval halts: the builder pre-approved plans that keep to the ticket and epic.
- **QA gate (builder, 2026-11-01):** after each change, the coordinator starts a separate QA session on the story's branch before anything merges. QA sends its findings straight to the story's session, which fixes them; QA re-checks until it passes.
- **Merging is approved:** when a story is green (0-warning build, all tests, NativeAOT publish) and QA has passed, its session merges it into `develop` from the main folder with `--no-ff` and `<type>(<scope>): merge <ref>-<slug>`, then commits `tickets.py mark <epic> <ref> done` on `develop`. **Never push.**
- **Releases:** at each epic's end (after its refactor sweep), the epic file gets `status: done` (it gates later epics) and a release session runs `git flow release start 0.<epic>.0` / `finish` in the main folder, tagging `v0.<epic>.0`, and leaves `develop` checked out there. git flow writes default merge messages ("Merge branch 'release/…'" and "Merge tag …"). Before anything builds on them, reword both to `chore(release): merge release 0.<n>.0` and `chore(release): merge v0.<n>.0 back into develop` with `git commit-tree` (same tree and parents), then `git update-ref` with the old value as a guard, and re-tag (as done for v0.4.0).
- **HITL checks:** a session automates what it can (synthetic input, injected keys, scripted players, logs, screenshots of its own windows) and records the rest in the Human Check Queue below instead of waiting. The story can still be marked done; the queue is the builder's to work through on return.
- **Unsliced epics (4–8):** a slicing session runs Sofia (`bmad-agent-po`) to break the epic into stories, choosing defaults where the PRD and architecture leave a gap, and lists each such choice in the Decisions Awaiting Review below.
- The PC is kept awake and unlocked while sessions work (the app's keep-awake hold plus a display-required holder). Never change Windows settings.
- Commit at every checkpoint and keep each plan's log current; the usage limit can land at any time.
- **Refactor sweeps keep forward hooks (2026-11-04):** a sweep must not delete code as "unused" when a later, not-yet-built ticket or the epic Notes depend on it. Before removing a type or member, grep the ticket tree (`_bmad-output/initiative-replay-buffer/tickets`) for its name. Epic 4's sweep deleted `RingGenerations.Restart`, and 6.6 had to restore it (`c7d7158`).
- **Lean tests (builder, 2026-11-03):** this is a personal project with no end users or stakeholders. Stories write a simple suite that verifies the functionality: one or two happy-path tests per AC, plus a test for any bug that really bit. No exhaustive edge-case tables, no long real-time waits, no benchmark-style assertions in the default run. QA doesn't fail a story for thin tests unless a core function is untested. Slow, hardware-bound or flaky tests go in the opt-in category that the test-trim work sets up (see `CLAUDE.md` "Tests" once it merges).
- **Model and effort per task (builder, 2026-11-02):** set them when starting a session (`start_session` `model`/`effort`) or, for a pool worker, before sending its brief (`set_session_model`/`set_session_effort`). Stories run on Opus (`claude-opus-5-5`), at high effort when the ticket's risk is high and at the default otherwise. QA rounds, merges, releases and syncs with develop run on Sonnet (`claude-sonnet-5-5`). A re-check after QA fixes (round 2 onward) runs at low effort. A story session that is told to merge may switch itself to Sonnet first.
- **Trello board (builder, 2026-11-03):** the private board [ReplayBuffer](https://trello.com/b/Q3TeryFd/replaybuffer) has one card per ticket, in lists by status (Backlog, Ready, In progress, In QA, Done). Its ids are in `trello-board.md` beside this file. The coordinator moves a card at each step: a story handed to a session goes to In progress, READY FOR QA goes to In QA, and a merge marked done goes to Done. Cards whose prerequisites are newly met move from Backlog to Ready. When a card reaches Done, the coordinator detaches its labels. Only the coordinator updates the board; story and QA sessions don't.
- **Wake the coordinator (2026-11-03):** the app wakes the coordinator only once *every* session it started is idle. So a QA pass or a READY FOR QA used to sit unseen while other sessions were still working, and the pipeline stalled. From now on, every story, QA, merge and chore session sends the coordinator a one-line cross-session message (SendMessage `to` = `local_0d27eb4a-e1f6-49b5-9d55-0b905e484b32`) at each hand-off point: READY FOR QA (branch and tip), the QA verdict (PASS or FAIL and count), and MERGED (commit). A cross-session message wakes the coordinator at once. Every brief includes this.
- **Scoped tests (builder, 2026-11-02):** don't run the full graphics or audio pipeline suites unless the change needs them. Run the 0-warning Release build, then only the test projects the diff touches plus their direct dependents (e.g. a UI change runs `ReplayBuffer.App.Tests`, not `Engine`, `Platform.Capture`, `Media` or `Platform.Audio`). The full `dotnet test --solution`, GPU capture runs and `bench` captures happen only when the diff touches the capture, encode, mux or audio path, or an AC needs the measurement. The NativeAOT publish runs only when engine code changed. Say in the report which projects ran and why the rest were skipped.

## Worker pool (builder, 2026-11-02)

The app starts a new session only from a turn the builder began. A READY FOR QA report, a merge or any other automated event can't start one. So that the run never waits on the builder, the coordinator hands new tasks to idle sessions it already started:

1. If the builder wrote in this turn, start a new session as usual. Otherwise:
2. Pick an idle worker from the table below that holds no queued message and isn't pinned or open on screen.
3. Clear it (`clear_session`) so it starts with fresh context. If the clear is refused, send the task without clearing and note it in the Log.
4. Send the full brief by `SendMessage`, the same brief a new session would get. Its first step: in its own worktree, discard nothing, check `git status` is clean, then cut the task's branch from `develop` (`git flow feature start ...`) or, for QA, check out the story's tip.
5. Note in the Queue's Session column which worker took the task, and retitle the worker (`set_session_title`) to its new task. A finished session is retitled "Done: <task> (merged|passed)", and an idle pool worker "Pool: idle (was <task>)".

Workers have Remote Control off, which `clear_session` requires. Sessions that are working keep Remote Control on.

## Per-session procedure (stories)

1. Read this file, `CLAUDE.md`, the ticket via `tickets.py find <ref>`, and the epic file.
2. `git flow feature start <ref>-<slug>` in the session's own worktree (cut from `develop`). For 1.14 only: switch to the existing `feature/1.14-benchmark`.
3. Run `bmad-build-auto` with the ticket ref.
4. Verify, scoped per the standing decision: `dotnet build ReplayBuffer.slnx -c Release` (0 warnings), `dotnet test` on the affected test projects only, `pwsh tools/publish-engine.ps1` (0 IL warnings) only when engine code changed. Real-time timing tests that fail only under GPU load get one rerun.
5. Commit, send the coordinator a one-line `READY FOR QA` message (see "Wake the coordinator"), then end the turn with a report that begins `READY FOR QA`: the branch, its tip commit, the verification results, and anything queued for the builder. Don't merge yet.
6. Fix each QA finding that arrives as a cross-session message, commit, and report `READY FOR QA` again.
7. When the coordinator says QA passed: merge into `develop` from the main folder with exactly `git -C %USERPROFILE%/Documents/repos/ReplayBuffer merge --no-ff feature/<ref>-<slug> -m "..."` (the builder's user-settings allow rule covers only `git [-C <main>] merge --no-ff feature/*`; any other form is blocked by auto mode), mark the ticket done, commit, and update this file's Queue, Log and queues. Don't push.

## QA procedure

The coordinator starts a fresh QA session in its own worktree, cut from the story's branch, once that session reports `READY FOR QA`. QA:

1. Reads this file, `CLAUDE.md`, the ticket (`tickets.py find <ref>`), the epic file, and the story's plan, its ACs above all.
2. Reviews the diff against `develop` for unmet ACs, broken `CLAUDE.md` rules and bugs. Thin tests are a finding only when a core function is untested (lean-tests rule).
3. Runs the scoped verification itself (0-warning Release build, the affected test projects, the NativeAOT publish only when engine code changed), plus each AC that can run without a person. For a HITL story it also runs the automated proxy the story describes.
4. Changes no code. It sends its findings as one cross-session message (`SendMessage`, `to` = the story session's id) listing each problem's location, what goes wrong, and the evidence, then ends with a report that begins `QA PASS` or `QA FAIL` and gives the count.
5. On a re-check, verifies the fixes and anything they touched.

The coordinator logs each QA round in the Log below.
